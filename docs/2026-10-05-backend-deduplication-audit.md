## 保持的兼容边界

- 所有现有 URL、权限键、成功状态码和响应字段保持原有契约。验证异常只在原先对应的路由中映射，不将全部错误改为统一格式。
- 商品分析与补货店铺查询仍带 `userId`，单店铺查询仍带 `id + userId`；统计仍限定当前用户及 `isActive: true`，零上传店铺继续返回 `0` / `null`。
- 日报上传继续按周期、币种、空商品行的顺序拒绝；保留原币种错误文案和写入前校验。廉价周期检查继续保留，以保护错误优先级。
- 权限、使用量事务、缓存失效、上传版本和计划并发控制留在原调用处。
- V2 商品规格、实际库存以及站点合并保持原样；V3 库存回填的有限成本检查及模拟库存的未知成本 `NaN` 保留各自语义。
- GLM 普通请求采用配置超时，流式请求继续采用固定流式超时；仅流式附带 `Accept`、`stream` 与快速模式参数，温度 `0` 不被默认值覆盖。
- SSE 已发送响应头后的错误分支保持原处理；Shopee 原始字节验签及商品原子 JSON 中间件没有套用普通 JSON 错误包装。
- 路由包装器默认采用标量路由参数类型；未来通配符数组参数需显式声明相应 `Params` 类型。回归测试覆盖两种类型用法。

重构前全量基线：75 个套件、1095 项测试通过；4 个 PostgreSQL 集成套件、13 项测试跳过。首次沙箱运行的 4 个 HTTP 套件因本地监听 `EPERM` 失败，在允许临时 localhost 端口的环境补跑后基线全绿。

`npm run build` 与 `git diff --check` 通过。改动经过代码审查及安全审查，审查重点为错误响应兼容、用户隔离、默认字段覆盖顺序、上传校验顺序和流式请求边界。

跳过的测试需要独立的 `USAGE_TEST_DATABASE_URL`，本次未配置：`usageEvents.postgres.test.ts` 4 项、`usageReport.postgres.test.ts` 4 项、`usageHistory.postgres.test.ts` 2 项、`aiUsage.postgres.test.ts` 3 项。不能把单元测试中的事务替身视为真实 PostgreSQL 行锁验证。

外部请求使用测试替身，HTTP 测试使用临时本地端口。未调用真实 AI、元仓、Shopee、采集或付费服务，未修改业务数据库。

## 审查中发现的剩余问题

| 文件 / 范围 | 发现与处理边界 |
| --- | --- |
| `services/aiUserConfig.ts` 与自定义 GLM 服务地址 | **既有高风险，非本轮引入**：配置个人 Key 后，服务地址仅校验 HTTP(S) 和 URL 内嵌凭据，未限制服务器回环、私网或重定向目标。具有相应 AI 权限的账号可使后端向内部地址发送请求，存在 SSRF 风险。需单独制定可用服务来源及出站限制，并验证重定向/DNS，以兼顾个人服务的配置需求；本次未执行真实内网请求或更改来源策略。 |
| `backend/scripts/importFinanceData.ts` | 历史一次性脚本使用硬编码 Windows 路径、全表 `deleteMany({})`，写入未提供当前模型要求的 `userId`。本轮没有运行；修复前不能作为可靠导入入口。应明确用户归属及替换范围后单独处理。 |
| `webhook-listener.py` | 未配置环境变量时仍使用固定默认 webhook 密钥；Content-Length 和 JSON 解析异常未处理，部署同步阻塞单线程监听器。属于部署安全与可用性修复，需单独明确配置和执行方式。 |
| 补货 V3 与利润模板大模块 | 剩余复杂度主要来自计划快照、逐日模拟和严格金额/物流契约。继续拆分应围绕明确业务职责；纯搬文件或通用数值校验不能代替减少实际重复。 |
| 长期进程缓存 | Dashboard loader 与元仓商品索引的缓存回收策略可单独评估；改变淘汰规则涉及运行行为，本轮未扩大范围。 |

以上问题来自静态代码审查，未推断生产环境的实际配置或已发生故障。本次完成了全后端的模块级审查及上述重复代码收敛，未声称消除全部历史风险。
